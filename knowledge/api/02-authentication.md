# 02 — Authentication

The Workfront API supports several authentication methods. The right choice depends on whether you're building a user-facing integration, a server-to-server job, or a one-off script.

## Summary of methods

| Method | Best for | Status |
|---|---|---|
| API key (`apiKey=`) | Quick scripts, legacy integrations | Deprecated — avoid for new work |
| Session login (`/login` endpoint) | Browser-context, cookie-based | Deprecated — avoid |
| OAuth2 authorization code | User-context integrations (user grants access) | Recommended |
| OAuth2 JWT / machine-to-machine | Server daemons, Fusion, scheduled jobs | Recommended for server-to-server |

Workfront officially states: *"Workfront no longer recommends the use of the `/login` endpoint or API keys."* For organizations on the Adobe Business Platform (IMS), password-based login via the API is not available at all.

## Required header on every authenticated request

All methods ultimately produce a session token. Pass it as a request header:

```
sessionID: <token_value>
```

The `sessionID` header is preferred over passing the token as a query parameter (`?sessionID=...`) because it does not appear in proxy logs, does not break URI-level caching, and is not subject to browser history exposure.

For **OAuth2 flows via Adobe IMS** (when authenticating through `https://ims-na1.adobelogin.com`), use the standard Bearer header instead:
```
Authorization: Bearer <access_token>
```

Check which endpoint issued your token — Workfront-native OAuth and Adobe IMS OAuth use different token types.

## Method 1 — OAuth2 authorization code (user-context)

Used when a real user is granting your app access on their behalf. The user is redirected to Workfront, logs in, and grants consent.

**Setup:** Workfront admin creates an OAuth2 application of type "Web Application" or "Single Page Application" in **Setup → System → OAuth2 Applications**. Creates a Client ID and Client Secret (store the secret immediately — Workfront will not show it again).

**Flow:**

1. Redirect the user to:
   ```
   https://<domain>.my.workfront.com/integrations/oauth2/authorize
     ?client_id=<CLIENT_ID>
     &redirect_uri=<REDIRECT_URI>
     &response_type=code
   ```

2. Workfront redirects back to your `redirect_uri` with `?code=<auth_code>`. The code is valid for **2 minutes**.

3. Exchange the code for tokens:
   ```
   POST https://<domain>.my.workfront.com/integrations/oauth2/api/v1/token
   Content-Type: application/x-www-form-urlencoded

   grant_type=authorization_code
   &code=<auth_code>
   &client_id=<CLIENT_ID>
   &client_secret=<CLIENT_SECRET>
   &redirect_uri=<REDIRECT_URI>
   ```

4. Response:
   ```json
   {
     "token_type": "sessionID",
     "access_token": "<token>",
     "refresh_token": "<refresh_token>",
     "expires_in": 0,
     "wid": "<workfront_user_id>"
   }
   ```

5. Use `access_token` as the `sessionID` header on subsequent API calls.

**Refreshing:** POST to the same token endpoint with `grant_type=refresh_token` and `refresh_token=<stored_refresh_token>`. Workfront does not store your refresh token — you must store it.

**Scopes:** Workfront's own OAuth2 implementation does not require specifying scopes in the authorization URL.

## Method 2 — OAuth2 JWT / machine-to-machine (server-to-server)

Used for daemons, scheduled jobs, and integrations where no human is granting consent. A service account authenticates with a certificate instead of a password.

**Setup:** Admin creates an OAuth2 application of type "Machine to Machine (JWT Flow)" in **Setup → System → OAuth2 Applications**. A public/private key pair is generated (or provided by the integrator).

**Flow:**

1. Construct a JWT with these claims:
   - `iss` — Client ID from the OAuth2 app
   - `sub` — User ID of the Workfront user who generated the public key
   - `exp` — Expiration (seconds since Unix epoch); short-lived recommended (a few minutes)

2. Sign the JWT with your private key using **RS256**.

3. Exchange for an access token:
   ```
   POST https://<domain>.my.workfront.com/integrations/oauth2/api/v1/jwt/exchange
   Content-Type: application/x-www-form-urlencoded

   client_id=<CLIENT_ID>
   &client_secret=<CLIENT_SECRET>
   &jwt_token=<base64-encoded-JWT>
   ```

4. Use the returned `access_token` as the `sessionID` header.

**Note on Adobe IMS JWT:** Adobe deprecated the JWT credential type in the Adobe Developer Console effective January 1, 2025. If your integration uses the Developer Console (IMS) rather than a Workfront-native OAuth2 app, migrate to OAuth2 Server-to-Server (client credentials) instead.

## Method 3 — API key (legacy, avoid for new work)

API keys are per-user, generated by the user or a Workfront admin. They provide the same access level as the user who owns the key.

Pass the key one of two ways:

**As a query parameter:**
```
GET /attask/api/v17.0/project/search?apiKey=<API_KEY>&status=CUR&status_Mod=eq
```

**As a header (`apiKey:`, not `sessionID:`):**
```
GET /attask/api/v17.0/project/search?status=CUR&status_Mod=eq
apiKey: <API_KEY>
```

**Important — don't use the `sessionID:` header for a raw API key.** The `sessionID:` header is for OAuth2-issued session tokens (which Workfront returns with `"token_type": "sessionID"` from the OAuth2 endpoints). Using `sessionID: <API_KEY>` with a raw API key returns `"You are not currently logged in."` Empirically verified on v17.0, 2026-05.

**Write operations require apiKey in the query string.** `POST`/`PUT`/`DELETE` calls that pass `apiKey` in the form-encoded body return `AuthenticationException: {0}`. Move it to `?apiKey=<key>` on the URL. `GET` accepts either. Empirically verified on v17.0 preview, 2026-05.

```
# ❌ Fails with AuthenticationException
curl -X POST "https://<host>/attask/api/v17.0/optask" \
  --data-urlencode "apiKey=<key>" --data-urlencode "name=Test"

# ✅ Works
curl -X POST "https://<host>/attask/api/v17.0/optask?apiKey=<key>" \
  --data-urlencode "name=Test"
```

**Lifetime:** Configurable by admins; default is monthly expiration. Production keys are copied to Preview during weekly refreshes (Preview keys are overwritten).

**Max per org:** API keys are per-user. Admins can revoke all keys system-wide from **Setup → System → Customer Info → API Key Settings**.

Only use API keys for quick one-off scripts or when your org has existing integrations you haven't migrated yet.

## Creating API credentials within Workfront

This section covers creating credentials directly inside Workfront (i.e., not via Adobe Developer Console). Use this path for orgs on the *Workfront-native* identity platform. For orgs on the **Adobe Business Platform (IMS)** — where users log in via Adobe ID — see the next section.

### OAuth2 Application — Web Application type (user-context / authorization code)

Admin only. Allows your app to act on behalf of a user who grants consent.

1. Navigate to **Main Menu → Setup → System → OAuth2 Applications**.
2. Click **Create app integration**.
3. Select **Web Application** and click **Next**.
4. Fill in the required fields:
   - **Name** — human-readable label for the app (e.g., "CRM Integration - Prod").
   - **Redirect URLs** — one or more URIs Workfront will redirect to after user consent. Must match exactly what your app sends in the authorization request.
   - **Description** (optional) — internal notes.
5. Click **Create**. Workfront generates a **Client ID** and **Client Secret**.
6. **Copy the Client Secret immediately.** Workfront will not show it again. If you lose it, you must delete it and generate a new one (existing tokens issued under the old secret continue to work until they expire, but no new tokens can be issued).
7. Optionally configure token expiration: absolute expiration and inactivity-based expiration are both configurable on the app detail page.

**Client Secret recovery:** There is none. Store it in a secrets manager (e.g., Azure Key Vault, AWS Secrets Manager, 1Password) at creation time. To rotate: open the app, delete the existing secret, generate a new one, update all consuming integrations before the old tokens expire.

### OAuth2 Application — Single Page Application type

Same navigation as above; select **Single Page Web Application** instead. Uses the PKCE flow (no client secret — the PKCE code verifier replaces it). Suitable for browser-based apps that cannot safely store a client secret.

### OAuth2 Application — Machine to Machine type (JWT / server-to-server)

Admin only. For daemons, scripts, and scheduled jobs that run without a human user granting consent.

1. Navigate to **Main Menu → Setup → System → OAuth2 Applications**.
2. Click **Create app integration**.
3. Select **Machine to Machine Application** and click **Next**.
4. Enter a **Name** and click **Create**.
5. On the app detail page, scroll to **Public Keys**. Either:
   - Click **Generate a public/private key pair** — Workfront generates both; you download the private key once (store it immediately; it is not recoverable from Workfront). Workfront retains the public key.
   - Or upload an existing public key if you generate the key pair externally (recommended for key rotation workflows where you control the private key lifecycle).
6. Note the **Client ID** and **Client Secret** shown on the page — same recovery caveat as above.

**Key rotation:** Generate or upload a new public key before the old one expires. You can have multiple active public keys on one app, which enables zero-downtime rotation: deploy the new private key to your integration, confirm it works, then delete the old public key from the app.

**Org limit:** A Workfront org can have a maximum of **10 OAuth2 applications** at one time across all types.

### API key — admin path (generate for any user)

1. Navigate to **Main Menu → Setup → System → Customer Info**.
2. Scroll to **API Key Settings**.
3. Select the user from the user picker and click **Generate API Key**.
4. Copy and share the key securely — it is shown once in this flow.

To set expiration for all keys: in **API Key Settings**, configure the **"API keys expire in"** dropdown (default is monthly). You can also enable **"Remove API key when a user's password expires"**.

To revoke keys: in **API Key Settings**, you can remove a specific user's key or click **Remove All API Keys** to invalidate every key org-wide (disruptive — warn integrators first).

### API key — self-service path (user generates their own)

Users can view (and in some configurations generate) their own API key from **Main Menu → Profile → (your avatar menu) → Edit Profile → API Keys tab**. Availability of the self-service tab depends on org configuration.

### Recommended hygiene

- Set an absolute expiration on OAuth2 app tokens (not just inactivity-based) — long-lived tokens increase blast radius if a credential leaks.
- Rotate client secrets and public keys on a schedule (annually at minimum), or immediately after any team member who had access departs.
- Give M2M / service-account users the minimum Workfront access level needed (Requestor or Contributor in most cases).
- Audit active OAuth2 apps quarterly via **Setup → System → OAuth2 Applications** — delete apps no longer in use.

## Creating API credentials in Adobe Developer Console

Use this path when your Workfront org is on the **Adobe Business Platform (IMS)** — i.e., users authenticate via Adobe ID. You can confirm this by checking whether your Workfront login page redirects through `auth.services.adobe.com` or `ims-na1.adobelogin.com`. If users log in directly at `<org>.my.workfront.com` without an Adobe ID redirect, use the Workfront-native path above instead.

### When to use this path vs. the native path

| Use Adobe Developer Console | Use Workfront-native OAuth2 Apps |
|---|---|
| Org is on Adobe Business Platform (IMS) | Org is on Workfront-native identity |
| Integration must use IMS access tokens (`Authorization: Bearer`) | Integration uses `sessionID` header |
| Centralized Adobe credential management is required | Only Workfront is involved |

### Prerequisites

- You must be a **full IMS Org Administrator** in Adobe Admin Console — not just a Workfront product admin. Workfront does not support the Admin Console "Developer" role for this purpose; only Org Admins can create projects in the Developer Console.
- The Workfront product must be provisioned in your Adobe Admin Console with at least one product profile.

### Step-by-step: OAuth Server-to-Server credentials

Adobe deprecated JWT (Service Account) credentials as of June 30, 2025. Use OAuth Server-to-Server for all new integrations.

1. Go to [https://developer.adobe.com/console](https://developer.adobe.com/console) and sign in with your IMS Org Admin Adobe ID.
2. Click **Create new project** (or open an existing project for this integration).
3. Click **Add API**.
4. In the API catalog, find **Adobe Workfront** under the Experience Cloud category. Click it.
5. Choose **OAuth Server-to-Server** as the credential type. (If you see "Service Account (JWT)", do not select it — it is deprecated and no longer usable for new credentials as of mid-2025.)
6. Give the credential a descriptive name (e.g., "Workfront Sync - Production").
7. Select one or more **Product Profiles** — these control which Workfront data the technical account can access. Choose the profile(s) whose access level matches what the integration needs.
8. Click **Save configured API**.

### Credentials issued

After setup, the Developer Console project credential page displays:

| Credential | Where to find it | Notes |
|---|---|---|
| **Client ID** | Credential detail page | Stable; used in every token request |
| **Client Secret** | Credential detail page → "Retrieve client secret" | Shown once per viewing; rotate via "Add new secret" |
| **Technical Account ID** | Credential detail page | Identifies the service account user in Workfront |
| **Technical Account Email** | Credential detail page | The email of the auto-created Workfront user |
| **IMS Organization ID** | Top of the project page | Your Adobe Org ID (format: `<hex>@AdobeOrg`) |

### Getting an access token

```
POST https://ims-na1.adobelogin.com/ims/token/v3
Content-Type: application/x-www-form-urlencoded

client_id=<CLIENT_ID>
&client_secret=<CLIENT_SECRET>
&grant_type=client_credentials
&scope=openid,AdobeID,read_organizations,additional_info.projectedProductContext
```

Response:
```json
{
  "access_token": "<token>",
  "token_type": "bearer",
  "expires_in": 86399
}
```

Tokens are valid for approximately **24 hours**. Cache and reuse them until they expire rather than requesting a new token per API call (aggressive token creation can trigger IMS rate limiting).

### Using the token against Workfront's API

Pass the IMS access token as a Bearer header — **not** as a `sessionID` header:

```
GET https://<domain>.my.workfront.com/attask/api/v17.0/project/search?status=CUR&status_Mod=eq
Authorization: Bearer <access_token>
```

### Critical pitfall: technical account user must exist and have access in Workfront

Creating credentials in the Developer Console automatically provisions a user in Workfront whose email matches the **Technical Account Email**. This user:

- Is assigned Contributor access by default (very limited).
- Will receive `data: []` on API calls to objects it cannot see — the API returns 200 with an empty result, not a 403, making this easy to misdiagnose.
- Must be explicitly granted the access level, groups, teams, and sharing permissions appropriate for the integration.

**To configure the technical account user:**
1. In Workfront, search for a user containing `techacct` or search by the exact Technical Account Email from the Developer Console.
2. Adjust their access level, home group, and any sharing permissions as you would for a service account user.
3. To grant admin rights: in Adobe Admin Console, add the Technical Account Email as an admin of the relevant Workfront product profile.

## Credentials and where to find them

| Credential | Location |
|---|---|
| Client ID | **Setup → System → OAuth2 Applications** → app detail page |
| Client Secret | Same page — copy on creation; cannot be retrieved later |
| API key | **Setup → System → Customer Info → API Key Settings** (admin can generate for any user), or the user's own Profile → API Keys |
| Workfront domain | **Setup → System → Customer Info** |

## Sandbox vs production credentials

OAuth2 apps created in production are **not** automatically available in the Preview sandbox. Create a separate OAuth2 app in the Preview environment for testing. Credentials are environment-specific; don't share client secrets between production and sandbox.

## Common authentication errors

| Symptom | Likely cause |
|---|---|
| `"Invalid session ID."` in error response | Expired token, wrong token type, or token from a different environment (preview vs prod) |
| `401 Unauthorized` HTTP status | Missing `sessionID` header, or the token has expired |
| `403 Forbidden` | Valid token, but the authenticated user lacks access to the object |
| Redirect loop or "not logged in" on Adobe Business Platform orgs | IMS login is required; `/login` endpoint is disabled for these orgs |
| 200 response with `data: []` when records exist | User context issue — the authenticated user genuinely can't see those records; check sharing/permissions |

## General rule

Pick the method that matches the caller's identity:

- A **user** is doing something on their own behalf → user-context auth (OAuth2 authorization code).
- A **service** is doing something on behalf of itself or all users → server-to-server auth (JWT / machine-to-machine).
- A **one-off script** by a specific admin → API key is convenient but deprecation-track; use OAuth2 if you have the time.

When in doubt, prefer the method your org has already standardized for other Workfront integrations.
